Modeling

Turn a JuMP model into a Quicopt Program and encode it to bytes.

QuicoptClient.import_model — Function
import_model(m::JuMP.Model) -> `Program`

Convert a JuMP/MOI model into a Quicopt Program. Reads the model at the MOI level: each variable becomes a scalar VarDecl (:x{col}) with its bounds and domain (a Semicontinuous or Semiinteger set gives the domain with a hole: 0, or a value in the set's range); the objective and every constraint become Quicopt expressions (ScalarNonlinearFunction/affine/quadratic → the expression graph; EqualTo → Zero, LessThan/GreaterThan/Interval → Nonneg). The result is a flat Program (no index sets); ±Inf bounds pass through and mean unbounded in that direction.

Variables given a distribution with set_distribution are emitted as named source declarations instead of decision variables, their uses rewritten to source references; the scenario count and seed from set_scenarios ride along as model data. A model with no stochastic marks emits exactly what it always did.

Permutations (permutation), partitions (partition) and lookup tables (lookup_table) are emitted as structure declarations and parameter tables. Their handle variables are not decision variables, and their names must differ from the variables' and the random variables'. Blocks (block) are emitted as block declarations over their members.

source
QuicoptClient.encode — Function
encode(prog) -> Vector{UInt8}

Encode a Program to the (v1) bytes the service reads. Two encodings of one model can differ byte for byte and still mean the same thing — compare decoded Programs, never raw bytes.

Stochastic models

A stochastic model is an ordinary JuMP model with two decorations: variables given a distribution, and aggregators closing every stochastic subexpression before it reaches the objective or a constraint root.

using QuicoptClient, JuMP

m = Model()
@variable(m, 0 <= x <= 200)            # decision: how much to stock
@variable(m, demand)                   # random: what will be asked for
set_distribution(m, demand, :normal, 100.0, 15.0)
set_scenarios(m, 512; seed = 42)

@objective(m, Min, 3x + 10 * expectation(max(demand - x, 0)))
result = solve(m)

Using demand twice refers to the same draw — one name is one random variable; declare independent ones as separate variables. These models solve through the service only: the aggregator heads are symbolic, so attaching a local optimizer fails with an unsupported-operator error.

A chance constraint bounds a probability, so the comparison against the threshold is an argument of prob rather than part of its name — that way it can only attach to the quantity, not to the probability the constraint is already bounding:

@constraint(m, prob(demand - x, ≤, 0) >= 0.9)   # stock out in ≤ 10% of scenarios
QuicoptClient.set_distribution — Function
set_distribution(model, v, head::Symbol, params...; name = Symbol(JuMP.name(v)))

Give the JuMP variable v a distribution: a draw from head (an operator from the service catalog, e.g. :normal) with the given parameters, which may be numbers or deterministic JuMP expressions. A variable that has a distribution is no longer one the solver chooses — it becomes a named random variable, and every use of v in the objective or constraints refers to the same draw (per scenario). Declare independent random variables separately.

Do not put bounds or integrality on v — it carries a distribution, not a domain — and close every stochastic subexpression with an aggregator (expectation, cvar, prob) before it reaches the objective or a constraint root.

set_distribution(model, v, data::AbstractVector{<:Real}; name = …)

The empirical distribution: v takes the given scenario column, one value per scenario (length(data) must equal the count passed to set_scenarios). Several empirical columns are aligned by scenario index, so jointly-drawn columns preserve their correlation.

source
QuicoptClient.set_scenarios — Function
set_scenarios(model, n_scenarios; seed = nothing)

Set the number of scenarios of the sampled instance to n_scenarios (and optionally the draw seed, ≥ 1). Both are model data: they pin the instance, so two solves of the same model see the same draws. Unset values fall back to the server's defaults (one scenario; its documented default seed).

source
QuicoptClient.expectation — Function
expectation(x) -> NonlinearExpr

The expected value E[x] over the scenarios — the basic stochastic → deterministic aggregator. Symbolic: JuMP stores the node and the service evaluates it; attaching a local optimizer to a model containing one will fail with an unsupported-operator error, which is expected.

source
QuicoptClient.cvar — Function
cvar(x, α) -> NonlinearExpr

The conditional value-at-risk of x at level α ∈ (0, 1) — the expected value of x over its worst (1 − α) tail. α must be a plain number.

source
QuicoptClient.prob — Function
prob(x, ≤, τ) -> NonlinearExpr
prob(x, ≥, τ) -> NonlinearExpr

The probability that x ≤ τ (resp. x ≥ τ): the fraction of scenarios in which the comparison holds. This is the aggregator behind a chance constraint —

@constraint(m, prob(demand - stock, ≤, 0) >= 0.9)

reads as demand is met in at least 90% of scenarios. The relation is an argument rather than part of the name so that it can only bind to x: written as prob_atmost(x, τ) it would compete with the bound on the probability itself, which the constraint already carries.

Only ≤ and ≥ have scenario counterparts (<= and >= are the same functions in Julia, so either spelling works); τ must be a plain number.

Orderings and lookup tables

A permutation places items in as many slots, one item per slot, both numbered from 1: for a route, the items are the stops and the slots the visits. Its item_at and slot_of are expressions whose values the service chooses, and a lookup_table indexed with them reads data at the positions they pick. The result carries each permutation's arrangement both ways round, as result.structures.<name>.item_at and .slot_of. A model with a permutation or a lookup table is solved by a search, so its status is "heuristic".

QuicoptClient.permutation — Function
permutation(model, name, n_items; start = nothing) -> Permutation

Declare an ordering as a decision: n_items items placed in as many slots, one item per slot. For a route the items are the stops and the slots are the visits, so slot 1 holds the first stop visited; for a machine the items are the jobs and the slots the positions in its queue.

name identifies the permutation in the result, as result.structures[name]. n_items is at least 2. start is the arrangement the service's search starts from: start[i] is the slot of item i, so it holds each of 1:n_items once. Left out, item i starts in slot i.

A model with a permutation is solved by a search, so its result has the status "heuristic".

Example

Five stops along a road; find the shortest route through all of them that visits stop 4 before stop 1:

using QuicoptClient, JuMP

position = [0, 3, 1, 4, 2]                        # km along the road, stops 1 to 5
m = Model()
dist  = lookup_table(m, :dist, [abs(a - b) for a in position, b in position])
route = permutation(m, :route, 5)
precede!(route, 4, 1)                             # stop 4 is visited before stop 1
@objective(m, Min, sum(dist[item_at(k, route), item_at(k + 1, route)] for k in 1:4))

result = solve(m)
result.objective                                  # 4.0
result.structures.route.item_at                   # [4, 2, 5, 3, 1]: the stops in the order visited
source
QuicoptClient.Permutation — Type
Permutation

A permutation declared by permutation: items placed in as many slots, one item per slot, both numbered from 1. P.n_items is the number of items. Read it with item_at and slot_of; constrain it with precede!.

source
QuicoptClient.item_at — Function
item_at(slot, P::Permutation) -> NonlinearExpr

The item in slot slot of the permutation P, an expression whose value the service chooses. For a route whose items are stops, item_at(1, route) is the first stop visited. Index a lookup_table with it to read data about that item. slot is a whole number from 1 to the size of P; broadcast for several, as in item_at.(1:4, route).

source
QuicoptClient.slot_of — Function
slot_of(item, P::Permutation) -> NonlinearExpr

The slot that item item is placed in, an expression whose value the service chooses. For a route whose items are stops, slot_of(3, route) is when stop 3 is visited. item is a whole number from 1 to the size of P.

source
QuicoptClient.precede! — Function
precede!(P::Permutation, before, after) -> Permutation

Require item before to be in an earlier slot of P than item after: a pickup before its delivery, or a job before the job that needs its output. The service only considers arrangements that meet every such requirement, so every solution meets it. Requirements that contradict each other, such as 1 before 2 and 2 before 1, are an error.

source
QuicoptClient.lookup_table — Function
lookup_table(model, name, values) -> LookupTable

Declare a table of data that can be indexed by decisions. A model sometimes needs a number from a table at a position that is not known yet: the distance between the first and the second stop of a route whose ordering the service is still choosing, or the price of an option an integer variable picks. A Julia array cannot be indexed this way; the table returned here can.

values is a vector (indexed table[i]) or a matrix (table[i, j]) of numbers, none of them NaN. Indexing with whole numbers only gives the entry itself; indexing with an expression, such as item_at or an integer variable, gives an expression whose value is the entry at the positions the service chooses. An index value that is not a whole number is rounded, and one outside the table is moved to its nearest end.

The whole table is sent with the model, so a very large table makes the request large.

source
QuicoptClient.LookupTable — Type
LookupTable

A table of data declared by lookup_table, to be indexed with expressions: table[i] for a vector, table[i, j] for a matrix.

Minimum loads, fees and blocks

A variable declared with JuMP's Semicontinuous(lower, upper) or Semiinteger(lower, upper) set is 0 or within the set's range, and nothing in between: a delivery of none, or of at least a minimum load. The range is the variable's bounds, so both ends must be finite and the variable carries no other bound. active is 1 when such a variable is not 0, which turns a fixed fee into one term.

A fee due once a total passes a threshold is JuMP's ifelse over a comparison, written inside a JuMP macro, where a comparison of variables is an expression: ifelse(sum(ship[w, :]) >= 1, opening[w], 0). Any of >=, <=, >, < and == works, and min and max cap or floor an expression in the same spirit.

A block names the variables of one subproblem, such as one customer's deliveries. Every solution the service returns satisfies the constraints that involve only one block's variables.

QuicoptClient.active — Function
active(x) -> NonlinearExpr

Whether the variable x is in use: an expression that is 1 when x is not 0 and 0 when it is. It is meant for a variable declared with JuMP's Semicontinuous or Semiinteger set, which is 0 or within the set's range, such as a delivery of either nothing or 10 to 25 units. A fee per delivery is then fee * active(x), and a model that is otherwise linear stays one the service solves exactly.

@variable(m, ship in Semiinteger(10, 25))         # none, or 10 to 25 units
@objective(m, Min, 2ship + 30active(ship))        # a price per unit and a fee per delivery
source
QuicoptClient.block — Function
block(model, name, vars)

Declare the variables vars as one block: the variables of one subproblem of the model, such as one customer's deliveries or one project's staffing. Every solution the service returns satisfies the constraints that involve only one block's variables, such as that customer's demand. A block changes nothing else about the model. Each variable is in at most one block and needs finite bounds; name identifies the block and must not be used twice.

Example

Three warehouses supply three customers. Each delivery is none or 10 to 25 units and costs 5 plus a price per unit; a warehouse that delivers anything pays its opening fee:

using QuicoptClient, JuMP

demand = [40, 30, 20]                             # units, customers 1 to 3
price = [1 3 4; 3 1 3; 4 2 1]                     # per unit, price[warehouse, customer]
opening = [60, 50, 40]                            # fee of warehouses 1 to 3
m = Model()
@variable(m, ship[1:3, 1:3] in Semiinteger(10, 25))   # every delivery: none, or 10 to 25 units
for c in 1:3
    block(m, "customer_$c", ship[:, c])
    @constraint(m, sum(ship[:, c]) >= demand[c])
end
@objective(m, Min, sum(price .* ship) + sum(5active(ship[w, c]) for w in 1:3, c in 1:3) +
                   sum(ifelse(sum(ship[w, :]) >= 1, opening[w], 0) for w in 1:3))

result = solve(m)
result.objective                                  # 300.0
[result.solution[Symbol("x", index(ship[w, c]).value)] for w in 1:3, c in 1:3]
# 3×3 Matrix{Float64}:
#  25.0  10.0   0.0
#   0.0   0.0   0.0
#  15.0  20.0  20.0

Warehouse 2 stays closed. Warehouse 1 sends its full 25 units to customer 1 and the minimum of 10 to customer 2; warehouse 3 covers the rest. Without the minimum load, the cheapest plan would cost 295 and send customer 2 a delivery of only 5 units from warehouse 1.

The opening fee is JuMP's ifelse over a comparison, written inside a JuMP macro (@objective, @expression, @constraint), where a comparison of variables is an expression; any of >=, <=, >, < and == works.

Groups

A partition puts each item into one of several parts, both numbered from 1: people into teams, jobs onto machines. Its part_of is the part an item is in and its size_of how many items a part holds. The result carries both, as result.structures.<name>.part_of and .size_of.

QuicoptClient.partition — Function
partition(model, name, n_items, n_parts; start = nothing) -> Partition

Declare a split into groups as a decision: each of n_items items goes into one of n_parts parts. The items might be people and the parts teams, or jobs and the machines that run them. A part may stay empty.

name identifies the partition in the result, as result.structures[name]. n_items is at least 1 and n_parts at least 2. start is the assignment the service's search starts from: start[i] is the part of item i, each in 1:n_parts. Left out, item i starts in part 1 + (i - 1) % n_parts.

A model with a partition is solved by a search, so its result has the status "heuristic".

Example

Six players of strengths 7, 5, 4, 3, 2 and 1 form a team of four and a team of two, as evenly matched as possible:

using QuicoptClient, JuMP

strength = [7, 5, 4, 3, 2, 1]                     # of players 1 to 6
m = Model()
teams = partition(m, :teams, 6, 2)                # 6 players into teams 1 and 2
@expression(m, total[t = 1:2], sum(ifelse(part_of(p, teams) == t, strength[p], 0) for p in 1:6))
@constraint(m, size_of(1, teams) == 4)            # team 1 has four players
@objective(m, Min, max(total[1], total[2]))

result = solve(m)
result.objective                                  # 11.0
result.structures.teams.part_of                   # [2, 1, 2, 1, 1, 1]: each player's team
result.structures.teams.size_of                   # [4, 2]: how many players in each team

Players 1 and 3 (7 + 4) make up the team of two, and the other four also add up to 11.

source
QuicoptClient.Partition — Type
Partition

A partition declared by partition: items placed in parts, both numbered from 1. P.n_items is the number of items and P.n_parts the number of parts. Read it with part_of and size_of.

QuicoptClient.part_of — Function
part_of(item, P::Partition) -> NonlinearExpr

The part that item item is in, an expression whose value the service chooses: a whole number from 1 to the number of parts of P. Index a lookup_table with it to read data about that part. item is a whole number from 1 to the number of items of P; broadcast for several, as in part_of.(1:5, teams).

source
QuicoptClient.size_of — Function
size_of(part, P::Partition) -> NonlinearExpr

How many items part part of P holds, an expression whose value the service chooses: a whole number from 0 to the number of items. part is a whole number from 1 to the number of parts of P.
